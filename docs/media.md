# README media

The hero images and the GIF in `docs/media/` are generated by
`scripts/media/build.ts` from the real extension running against
`fixtures/demo.html`.

```sh
pnpm media                 # build the extension, capture, render everything
pnpm media --only hero     # or: gif
pnpm media --render        # re-render from the last capture, no browser driving
```

`--render` is for changing the window frame, the pointer or the timing of the
loop seam without capturing again. After changing the panel, the demo page or
the scripted steps, run plain `pnpm media`.

Needs ffmpeg on PATH. Captures, stage pages and frames go to `.media-cache/`
(gitignored); only the files in `docs/media/` are committed.

## What it makes

| File | What |
| --- | --- |
| `hero-light.png`, `hero-dark.png` | 1920x1080. A browser window with the demo page on the left and Motion Inspector in Chrome's side panel on the right, paused at 1150 ms, with the `load` row hovered so the progress bar is outlined on the page. Transparent outside the window. The README picks one with `<picture>` and `prefers-color-scheme`; page, panel and window chrome all follow the theme. |
| `demo.gif` | About 16 s, 1100x805, 20 fps, light theme on a neutral grey backdrop so one file works in both README themes. The page animating, pause, hover the waveform (the preview time changes in the readout's slot), drag to scrub, hover and open `load`, scroll to Export, switch CSS → Motion → GSAP, copy. |

## Approach

Nothing in the images is mocked up except the browser window around them and
the pointer. Each state is a screenshot of the real panel and the real page.

1. **Serve.** `fixtures/demo.html` is served as `http://localhost:3000/deploys`
   through Playwright's request routing (no server, no port), so the panel's
   header and the omnibox read like a project on a dev server. GSAP and Motion
   come from `node_modules`. The page has CSS keyframes, WAAPI with a
   `linear()` spring, GSAP and Motion, six identical skeleton pulses that group
   into one row, and nothing started by a timer, so scrubbing to the same time
   always draws the same frame.
2. **Capture.** Like `scripts/e2e.ts`, it loads `dist/chrome-mv3` into
   Playwright's Chromium and opens the panel page in a tab with
   `?tabId=<page tab>` at the side panel's size (Playwright can't screenshot
   the real side panel). The page and the panel are shot at the output's
   device pixel ratio (1.5 for the hero, 1.25 for the GIF), so they're drawn
   into the final image 1:1, never resampled.
3. **Drive the GIF frame by frame.** The GIF is built as a list of 20 fps
   frames, each naming a panel shot, a page shot and the pointer position.
   Whenever the pointer is over the panel, the real mouse is moved there and
   the panel is shot, so hover states, the waveform preview and the drag are
   exactly what the panel drew at that position. The page is shot again
   whenever it can change (scrubbing, hovering a row, opening one). The live
   part at the start is the one place that isn't captured live: the panel
   pauses, then scrubs every animation through 0, 50, 100 … 1950 ms with the
   scrubber's `mi-seek` test hook, and those page shots play under the live
   panel. That's the same time model a drag uses, and it makes the opening
   seconds identical on every run.
4. **Compose.** A stage page draws the window (tab strip, toolbar, omnibox,
   the side panel's rounded card and header) and places the shots on it. Every
   edge a shot sits on is a multiple of 4 CSS px for the GIF and 2 for the
   hero, so at 1.25x and 1.5x the shots land on whole device pixels and the
   text stays as sharp as Chrome drew it. For the GIF the stage has a
   `render(i)` function; Playwright calls it for each frame and screenshots.
   The loop seam fades the window's content to white and back in on the
   first frame while the pointer travels back, so no frame shows two states
   at once.
5. **Encode.** ffmpeg's two-pass palette, as in rpc-agent:
   `palettegen=stats_mode=diff`, then
   `paletteuse=dither=none:diff_mode=rectangle`. No dithering keeps flat UI
   colours flat and text clean, and only the changed rectangle of each frame
   is stored, which is why the GIF is around 1.3 MB. The hero PNGs keep alpha
   for the window shadow and are only recompressed.

Why not record the screen: a Playwright video or a screen recording runs at
the page's real timing, never matches between runs, needs trimming and
re-encoding, and can't show the real side panel either. Here the same capture
gives the same frames.

## Changing it

- The steps, pointer paths and how long each state is held are in
  `captureGif()`, numbered in order. `push(n)` holds the current frame for
  `n` frames (20 per second) and `glide(to, n)` moves the pointer over `n`
  frames, shooting the panel at each step.
- The hero's time and hovered row: `HERO_TIME` and `captureHero()`.
- Sizes: `HERO` and `GIF` (`layout(dpr, stage, window, panel width)`). Keep
  the window position, page width and panel width on the 4 px (GIF) / 2 px
  (hero) grid.
- The window chrome: `windowHtml()`, colours in `CHROME_THEME`.

After a change, look at a few frames:

```sh
ffmpeg -i docs/media/demo.gif -vf "select='eq(n\,45)+eq(n\,75)+eq(n\,110)+eq(n\,205)+eq(n\,300)',tile=1x5" -frames:v 1 /tmp/frames.png
```

`HEADED=1 pnpm media` shows the browser while it captures.
